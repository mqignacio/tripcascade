# Human Checkpoint Rules — TripCascade

Shared by **pi** and **Qoder**. Load before any Commitment/Money/Aftercare Atlas action. Source: `doc/PRD.md` §6 (Settlement Policy), `doc/SPECS.md` S-006 (FR-006). The policy engine is **deterministic code**; the LLM never decides money steps.

## 1. When a human MUST confirm

| Trigger | Rule | UI surface |
|---|---|---|
| **Above-cap settlement** | `fare_difference_cents > SETTLEMENT_CAP_CENTS` (default 5000 = S$50) -> **hold**, surface the proposed re-plan + total cost, execute only on explicit human approval (or reject). | Approve/Reject control on the affected node (FR-008). |
| **Payment summary** | Before any `order pay` executes (even auto-settle <= cap), the UI shows the fare-difference summary + `orderNo` + `amount_cents`. Auto-settled payments are audit-logged; the summary is visible inline after execution. | Inline audit-log entry + summary card. |
| **Any price increase** | If the re-plan's fare is higher than the original leg, the difference is computed and gated by the cap rule. A price *decrease* (refund) still routes through Aftercare policy-gating and is recorded. | Summary card with delta. |
| **Above-cap human verdict** | The approve/reject decision is recorded as a structured, reusable record (`outcome=human_approved|human_rejected`, `human_verdict` free text) -> the decision-learning log (FR-007). | Decision log panel. |

## 2. When a human is NOT needed

- **Auto-settle <= cap:** `fare_difference_cents <= SETTLEMENT_CAP_CENTS` -> the policy engine auto-executes the Atlas action + writes an audit-log record (`outcome=auto_settled`). No human in the loop. (This satisfies the deck's Level-4 benchmark: "autonomously settle the fare difference in real time.")
- **Discovery (search/offer/price):** read-only, ungated, safe to hammer in Sandbox.
- **Advisory node actions (hotels/activities):** impact analysis + drafted notification only; no Atlas booking call, no money, no checkpoint.

## 3. Hard rules

1. **The LLM never constructs the Atlas call body.** The policy engine builds it from structured data (`offer_id`/`orderNo`/`amount_cents`); the LLM only proposes *which* alternative and explains the rationale.
2. **Re-read the world before every write** (see `atlas_tool_protocol.md` §4.2): re-verify the offer before order; confirm order unpaid before pay.
3. **Assert the post-state** (see `coding_standards.md` §4): a 200 with an empty body is a fail. Confirm `orderNo` / `confirmation_id` / `ticketNos`.
4. **Every decision is recorded** (auto and human): `record_id, timestamp, node_id, action, amount_cents, cap_cents, outcome, human_verdict, reasoning_trace, model_tier_used, atlas_state_refs, reusable=true`. Today's human judgement is tomorrow's threshold (the bounded-autonomy loop learns).
5. **The cap is configurable** (`SETTLEMENT_CAP_CENTS` in `.env`), read by the policy engine, never generated by the LLM. Default 5000 cents (S$50).

## 4. Demo flow (the 3-minute story)

Leg 1 (PVG->NRT) fare diff S$30 (3000 cents) <= cap -> **auto-settled**, audit-log visible inline. Hotel (advisory) -> **drafted notification**, no booking. Leg 2 (NRT->PVG) fare diff S$120 (12000 cents) > cap -> **held**, Approve/Reject surfaced, traveler approves -> recorded. Decision log populated. This is the bounded-autonomy demo.
